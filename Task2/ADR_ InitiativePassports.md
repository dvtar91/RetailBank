# Задание 2 – Оценка готовности данных, размещения и выбор модели  

## ADR #1‑Выявление подозрительных операций (инициатива F)

### Контекст  

RetailBank обрабатывает около 20‑25 млн транзакций в месяц. По текущим правилам — пороговым фильтрам — выделяется часть операций, требующая проверки финансовым мониторингом. Подтверждённые схемы мошенничества редки (единицы в месяц), в то время как большинство помеченных транзакций остаются без окончательного решения.

Требуется автоматический классификатор, который будет:

* Оценивать вероятность подозрительности каждой операции в реальном времени;  
* Выдавать тип риска (транзит, обналичивание, дробление и пр.);  
* Добавлять метку в очередь на ручную проверку, но не принимать окончательное решение без участия человека (соответствие регуляциям).  

### Жёсткие ограничения  

| Ограничение | Требование |
|-------------|------------|
| **Персональные данные** | Все ПДн (номер счёта, ФИО, ИНН) должны находиться **on‑prem** и не вывозиться за пределы РФ. |
| **Latency** | Инференс ≤ 50 ms на каждое событие (требуется поддержка онлайн‑транзакций). |
| **Compliance** | Решение должно быть одобрено DPO и отделом юридического контроля; необходимо хранить аудит‑лог всех запросов к модели. |
| **Интерпретируемость** | Требуется возможность объяснить решение (SHAP‑анализ, правила‑постобработки). |
| **Объём данных** | Обучающий набор ≤ 30 k размеченных операций (по текущим ресурсам). |
| **Инфраструктура** | Возможность использовать GPU‑инференс в **гибридном** режиме (контур провайдера = Yandex Cloud, РФ‑регион). |

### Допущения и план получения меток

| № | Что требуется | Как будем получать | Ожидаемый срок | Примечание |
|---|----------------|-------------------|----------------|------------|
| **F‑1** | **Контрольная (стрaтифицированная) выборка** – случайные транзакции из всех каналов (по суммам, типу клиента, региону). | Data‑Engineering сформирует набор‑выборку размером **≈ 10 k** записей. | 2 недели | Будет использоваться только для валидации модели, не попадёт в обучающий набор. |
| **F‑2** | **Экспертная разметка подозрительности** (high‑quality, “clean / suspicious”). | Финмониторинг «размечает» выбранную контрольную выборку в течение 4 недель (≈ 3 часа / операцию). | 6 недель | После разметки будем вычислять коэффициент согласованности κ – целевой минимум 0,80. |
| **F‑3** | **Подтверждённые схемы мошенничества** (ground‑truth). | В течение 3 мес. собираются все случаи, завершившиеся официальным подтверждением (пример — внутренний регламент). Ожидается < 1 % от всех проверок. | 3 мес. | Эти метки используют только для окончательной оценки Recall/FNR. |
| **F‑4** | **Слабые метки (правила, AML‑API, эскалации)** – могут быть использованы как «weak‑label» для предтренинга. | Автоматически генерируются из текущих бизнес‑правил и внешних AML‑сигналов. | Непрерывно | Помечаются как `weak` и **не** участвуют в финальном тесте. |
| **F‑5** | **Согласование с DPO** – формальное разрешение на хранение и обработку ПДн в гибридном контуре. | Подача запрос‑письма в отдел комплаенса, подпись DPO. | 2‑нед период | До получения подписи все данные остаются в изолированном тестовом окружении. |

### Рассмотренные варианты размещения  

| Вариант | Плюсы | Минусы | Оценка по ограничениям |
|---------|-------|--------|------------------------|
| Public API (внешний SaaS) | Быстрая масштабируемость | Вывоз ПДн за пределы РФ → **неприемлемо** | **Отброшено** |
| Self‑hosting в облаке (AWS, GCP) | Гибкость, GPU | Данные покинут РФ → **неприемлемо** | **Отброшено** |
| **On‑prem** (выделенный сервер) | Полный контроль ПДн | Ограниченная масштабируемость, отсутствие GPU‑инференса | **Оставлен** (для предобработки) |
| **Гибрид (on‑prem + контур провайдера)** | ПДн остаются on‑prem, инференс в защищённом облачном контуре (GPU) | Требует организации защищённого канала и согласования DPO | **Выбран** |

#### Выбор модели

| Кандидат | Причина попадания в шортлист | Требуемые ресурсы | Приёмочные пороги |
|----------|-----------------------------|-------------------|--------------------|
| **LightGBM** | Проверенный в банковских задачах, быстрая инференс, легко объяснимый SHAP | CPU 2 vCPU + 8 GB RAM | Recall ≥ 0.85, FPR ≤ 0.05, latency ≤ 50 ms |
| **CatBoost** | Хорошая работа с категориальными признаками и missing‑values | CPU 2 vCPU + 8 GB RAM | Recall ≥ 0.85, FPR ≤ 0.05, latency ≤ 50 ms |
| **TabPFN (PyTorch)** | Возможный прирост Recall, быстрый предтренинг, использует GPU | GPU 1 × Tesla T4 | Recall ≥ 0.88, latency ≤ 40 ms (GPU) |

##### Процедура окончательного выбора  

1. **Обучение** на контрольной выборке (10 k операций, 5 % потенциальных схем).  
2. **5‑fold cross‑validation** → собираем Recall, Precision, ROC‑AUC, latency.  
3. **Business‑critical тест** – 1 000 новых операций в прод‑стриме, проверка после расследования.  
4. Выбираем модель, удовлетворяющую **Recall ≥ 0.85**, **FPR ≤ 0.05** и **latency ≤ 50 ms**.  
5. При отсутствии подходящей модели – увеличить объём контрольной выборки до 30 k и повторить.

### Путь получения сигнала‑метки  

| Шаг | Описание |
|-----|----------|
| **Шаг 1** – Экспертная разметка подозрительности | Финансовые аналитики маркируют каждую запись из контрольной выборки как *clean* / *suspicious* по **гид‑лайну**. |
| **Шаг 2** – Сбор подтверждённых схем | По мере завершения расследований фиксируются случаи, где схема подтверждена (ground‑truth). |
| **Шаг 3** – Слабые метки | Параллельно собираются сигналы из существующих правил, внешних AML‑API и отметок об эскалации (они считаются *weak*). |
| **Шаг 4** – Объединение | Создаётся итоговый тренировочный набор: **экспертные метки (high‑quality)** + **weak‑labels** (для предтренинга). **Подтверждённые схемы** остаются в отдельном hold‑out‑наборе для оценки Recall/FNR. |  

### Риски и план‑миграция  

| Риск | Как смягчаем |
|------|--------------|
| **Смещение отбора** (только правила → эксперты) | Вводим независимую **контрольную выборку** (A‑1) и **периодический пере‑оценочный цикл** (каждые 4 недели). |
| **Недостаток подтверждённых схем** (ground‑truth) | Планируем собрать **все** подтверждённые схемы за 3 мес. (A‑3). Пока их мало, будем использовать **низко‑доверительные** (low‑confidence) зоны для human‑review. |
| **Конфиденциальность** | Шифрование «на лету», отдельный VPN‑тunnel к гибридному GPU‑контурa, аудит‑лог. |
| **Низкая интерпретируемость** | SHAP‑анализ, правила‑постобработки, автоматическое отклонение при превышении порога важности признаков. |
| **Недостаток вычислительных ресурсов** | Планируем масштабировать GPU‑инстанс при необходимости; текущая конфигурация поддерживает 50 ms latency для LightGBM. |
| **Отсутствие подписи DPO** | Сразу после начала проекта формируем запрос‑письмо; до получения подписи данные остаются **только в тестовой среде**. |

#### Триггеры пересмотра

* **Recall < 0,80** в пилотных измерениях (на подтверждённых схемах).  
* **FPR > 0,07** в прод‑стриме.  
* **Отсутствие подписи DPO** более 30 дней после начала сбора данных.  
* **Выявление новых типов мошенничества**, не покрытых текущей разметкой (см. пункт F‑2).  
* **Регулятивные изменения** (например, новые требования к локализации данных).

---

#### Ожидаемые выгоды  

| Показатель | Ожидаемая экономия / выгода |
|------------|-----------------------------|
| Сокращение времени ручной проверки (12 min → 4 min) | ~ 30 M ₽/год (сокращение затрат на штат) |
| Уменьшение количества ложных блокировок (FPR ≤ 5 %) | ~ 5 M ₽/год (меньше жалоб, удержание клиентов) |
| Увеличение точности обнаружения схем (Recall ≥ 85 %) | Снижение штрафов regulator (≈ 10 M ₽/год) |

---

**Итог:** Флагманская инициатива готова к пилотному запуску в гибридном режиме с выбранным шортлистом моделей. Планируется 6‑недельный пилот, после которого будет принято решение о масштабировании в продакшн.

## ADR #2 – OCR‑оцифровка документов (инициатива A)

### Контекст  

Необходимо автоматически извлекать из загруженных сканов (PDF / JPEG) ключевые поля (ИНН, суммы, даты, подписи) для ускорения обработки кредитных заявок.

### Допущения и план сбора данных  

| № | Что планируем собрать | Как будем собирать | Ожидаемый объём |
|---|----------------------|--------------------|-----------------|
| **A‑1** | **Разметку полей** (bounding‑box + тип) | Внутренние аннотаторы размечают **1 500** уже существующих сканов (первичный набор). | 1 500 сканов |
| **A‑2** | **Новые сканы в пилот** (расширяющий набор) | В течение 4 недель система будет принимать **≈ 500 сканов/неделя** (≈ 2 000 сканов). | 2 000 сканов |
| **A‑3** | **Коэффициент согласованности κ** | После разметки первого набора два аннотатора сравнят результаты; планируем ≥ 0,80. | — |
| **A‑4** | **DPO‑согласование** | Оформляем запрос в юридический отдел, получаем подпись до начала пилота. | — |

> **Весь набор** будет храниться **on‑prem** (GPU‑сервер), чтобы соблюсти требование «данные не покидают РФ».

### Выбранный вариант размещения  

| Вариант | Плюсы | Минусы | Выбор |
|---------|-------|--------|-------|
| Облачный OCR SaaS | Высокая точность, отсутствие инфраструктурных затрат | Вывоз изображений за границу (не соответствует регуляции) | **Отброшено** |
| **Self‑hosted OCR** (Tesseract + GPU) | Полный контроль, данные остаются в периметре | Требуются ресурсы GPU, поддержка модели | **Выбран** |
| Гибрид (on‑prem + облачный сервис в РФ) | Возможность перераспределять нагрузку | Сложнее управлять согласованием | Возможен в будущем, но пока — **Self‑hosted** |

### Шортлист моделей  

| Кандидат | Почему в шортлист | Требуемые ресурсы | Целевые метрики |
|----------|-------------------|-------------------|-----------------|
| LayoutLMv3 (трансформер) | Превосходит традиционный OCR на полях с таблицами, поддержка русского | GPU A100 (64 GB VRAM) | F1 ≥ 0,95, latency ≤ 200 ms |
| Tesseract + правила (RegEx/списки) | Дешевый, быстрый, легко поддерживаемый, уже используется в прототипе | CPU 4 vCPU + 16 GB RAM | F1 ≥ 0,95, latency ≤ 120 ms |

**Процедура выбора** (по‑плану, без прежних утверждённых цифр):  

1. Обучить LayoutLMv3 на наборе B‑1 + B‑2 (transfer‑learning).  
2. Сравнить с Tesseract + правилами на hold‑out‑наборе (≈ 400 сканов).  
3. Выбрать решение, которое удовлетворит **целевые** метрики (F1 ≥ 0,95) и соответствует ограничениям по latency и инфраструктуре.  

## ADR #3 – Прогноз оттока клиентов (Churn) (инициатива B)

### Контекст  

Необходимо прогнозировать вероятность ухода клиента в течение квартала, чтобы формировать список для таргетированных удерживающих кампаний.

### Допущения и план получения меток  

| № | Что требуется | Как будем получать | Примерный срок |
|---|----------------|-------------------|----------------|
| **B‑1** | **Исторические подтверждённые оттоки** (ground‑truth) | Выгрузка из CRM всех случаев, где клиент действительно ушёл (около 9 k записей). | Уже имеется (исторический набор). |
| **B‑2** | **Слабые метки** (признаки оттока, но без подтверждения) | Автоматически генерируются из текущих бизнес‑правил и предсказаний предыдущих моделей (≈ 5 k). | Непрерывно |
| **B‑3** | **Контрольная случайная выборка** → проверка точности | Случайным образом выбираем **≈ 1 %** всех активных клиентов (≈ 2 k) и собираем их статус в течение квартала (opt‑out согласия). | 1 мес |
| **B‑4** | **Согласие клиентов (opt‑out) + подпись DPO** | Формируем юридический запрос, получаем подпись. | 2 неделя |

> Пока нет полного набора «слабых меток» с подтверждёнными оттоками, **Recall/Precision** будут рассчитаны только после завершения **B‑3** (control‑sample) и **B‑4** (юридическое согласование). Поэтому они объявляются **целевыми** (Recall ≥ 0,80, Precision ≥ 0,25).

### Выбранное размещение  

| Вариант | Плюсы | Минусы | Выбор |
|---------|-------|--------|-------|
| Облачный ML‑platform (AWS SageMaker) | Масштабируемость, автоматическое обучение | Данные ПДн попадут в облако за границу | **Отброшено** |
| **On‑prem** (XGBoost, CPU) | Полный контроль над ПДн, поддержка объяснимости | Нет GPU‑ускорения (не требуется для табличных данных) | **Выбран** |
| Гибрид (обучение в облаке, инференс on‑prem) | Возможность использовать более мощные ресурсы для пере‑обучения | Сложнее в управлении | Возможен в будущем, но пока **On‑prem** |

### Шортлист моделей  

| Кандидат | Почему в шортлист | Требуемые ресурсы | Целевые метрики |
|----------|-------------------|-------------------|-----------------|
| LightGBM | Быстрая, хороша для табличных признаков, легко объяснимая (SHAP). | 2 vCPU + 8 GB RAM | Recall ≥ 0,80, Precision ≥ 0,25, latency ≤ 30 ms |
| CatBoost (target‑encoding) | Автоматически обрабатывает категориальные признаки, часто даёт лучший AUC. | Аналогично LightGBM | Same |
| Deep FM (GPU) | Позволяет моделировать взаимодействия признаков, потенциальный прирост AUC. | 1 × Tesla T4 | Recall ≥ 0,80, Precision ≥ 0,25, latency ≤ 30 ms (GPU) |

**Процедура выбора** (по‑плану):  

1. Обучить все три модели на объединённом наборе **B‑1** + **B‑2**.  
2. Выполнить 5‑fold CV, собрать **целевые** метрики.  
3. Проверить модель на **hold‑out‑контрольной выборке** (B‑3) и убедиться, что **Recall ≥ 0,80** и **Precision ≥ 0,25**.  
4. Выбрать модель с лучшим **ROI** (расчёт выгоды от удержания vs. стоимость кампании) при выполнении целевых метрик.  

### Риски и триггеры пересмотра  

| Риск | Митигаторы |
|------|------------|
| Нехватка подтверждённых оттоков (ground‑truth) | Собирать **контрольный набор** B‑3, постоянно пополнять базу. |
| Data‑drift (изменение поведения клиентов) | Мониторинг PSI, регулярные пере‑обучения (каждый квартал). |
| Несогласие клиентов (opt‑out) | Выводим процесс получения согласия в интерфейс CRM, фиксируем процент отказов. |
| Регулятивные ограничения (доступ к ПДн) | Храним только анонимные признаки, DPO‑подпись получена (B‑4). |
| Пороговые целевые метрики не достигаются | При падении ниже целевых значений – **перейти к rule‑only** (добавить более жёсткие бизнес‑правила). |

#### Триггеры пересмотра  

* **Recall < 0,80** в проверке на контрольной выборке.  
* **Precision < 0,25** в том же тесте.  
* **Падение AUC** более чем на 0,05 по сравнению с базовым периодом.  
* **Регулятивные изменения**, требующие полной объяснимости (отказ от ML‑модели).

# Паспорт инициативы: Выявление подозрительных операций (флагман)

## Постановка задачи
* **Цель:** в реальном времени классифицировать каждую банковскую операцию по вероятности подозрительности и типу риска (транзит, обналичивание, дробление).
* **Выход:** метка `risk_score` (0‑1) + `risk_type` (категория). Метка направляется в очередь финмониторинга, но окончательное решение принимает человек.
* **Ограничения:** решение должно работать в режиме онлайн (latency ≤ 50 ms), сохранять полную конфиденциальность ПДн, предоставлять интерпретируемые объяснения.

## Качество данных
| Аспект | Оценка |
|--------|--------|

# Паспорт инициативы: Прогноз оттока клиентов (Retention)

## Постановка задачи
* **Цель:** предсказывать вероятность ухода клиента в следующем квартале, чтобы сформировать список для таргетированных retention‑кампаний.
* **Выход:** `client_id → churn_probability (0‑1)`. При пороге ≥ 0.6 клиент попадает в список рекомендаций.
* **Ограничения**:
   * модель должна быть объяснимой (importance‑фичи),
   * решения – только рекомендации (не автоматическое отказание), latency ≤ 30 ms, анонимизация данных перед передачей в облако.
   * **Batch‑режим** – прогноз рассчитывается один раз в сутки, поэтому latency ≤ 30 ms относится к времени инференса внутри батча, а не к пользовательскому отклику.  
   * Данные анонимизируются перед передачей в модель; все операции выполняются **внутри периметра банка (on‑prem)**.  


## Качество данных
| Аспект | Оценка |
|--------|--------|
| **Источник правильного ответа** | 1) Исторические метки оттока ≈ 9 k (надёжные, подтверждённые). 2) Слабые метки из контрольных выборок ≈ 5 k (потенциальные). |
| **Качество** | Разметка согласована двумя аналитиками (κ = 0.81). |
| **Объём** | 14 k примеров (≈ 5 % отток). |
| **Разметка** | Бинарный `churn / no_churn`. |
| **Смещение** | Исторические метки неполные → дополнительно вводится случайная контрольная выборка (1 % всех клиентов) для уменьшения смещения. |
| **Репрезентативность** | Покрывает все сегменты: размер компании, отрасль, регион, канал взаимодействия. |
| **Право использовать** | Требуется согласие клиентов (opt‑out) + подпись DPO; данные анонимизируются (удаляются ПДн). |
| **Владелец** | CRM‑команда + DPO. |
