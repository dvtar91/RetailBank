# Задание 2 – Оценка готовности данных, размещения и выбор модели  

## Контекст  

RetailBank обрабатывает ~20‑25 млн операций в месяц. Пороговые правила и внешние сигналы помечают ~35 тыс. операций, из которых финмониторинг успевает разобрать только ~10 тыс. (≈ 30 %). При этом подтверждённые схемы — единицы в месяц, а большинство помеченных операций остаются без окончательного вердикта.  

Требуется автоматический классификатор, который будет:

* Оценивать вероятность подозрительности каждой операции в реальном времени;  
* Выдавать тип риска (транзит, обналичивание, дробление и пр.);  
* Добавлять метку в очередь на ручную проверку, но не принимать окончательное решение без участия человека (соответствие регуляциям).  

## Жёсткие ограничения  

| Ограничение | Требование |
|-------------|------------|
| **Персональные данные** | Все ПДн (номер счёта, ФИО, ИНН) должны находиться **on‑prem** и не вывозиться за пределы РФ. |
| **Latency** | Инференс ≤ 50 ms на каждое событие (требуется поддержка онлайн‑транзакций). |
| **Compliance** | Решение должно быть одобрено DPO и отделом юридического контроля; необходимо хранить аудит‑лог всех запросов к модели. |
| **Интерпретируемость** | Требуется возможность объяснить решение (SHAP‑анализ, правила‑постобработки). |
| **Объём данных** | Обучающий набор ≤ 30 k размеченных операций (по текущим ресурсам). |
| **Инфраструктура** | Возможность использовать GPU‑инференс в **гибридном** режиме (контур провайдера = Yandex Cloud, РФ‑регион). |

## Рассмотренные варианты размещения  

| Вариант | Плюсы | Минусы | Оценка по ограничениям |
|---------|-------|--------|------------------------|
| Public API (внешний SaaS) | Быстрая масштабируемость | Вывоз ПДн за пределы РФ → **неприемлемо** | **Отброшено** |
| Self‑hosting в облаке (AWS, GCP) | Гибкость, GPU | Данные покинут РФ → **неприемлемо** | **Отброшено** |
| **On‑prem** (выделенный сервер) | Полный контроль ПДн | Ограниченная масштабируемость, отсутствие GPU‑инференса | **Оставлен** (для предобработки) |
| **Гибрид (on‑prem + контур провайдера)** | ПДн остаются on‑prem, инференс в защищённом облачном контуре (GPU) | Требует организации защищённого канала и согласования DPO | **Выбран** |

### Выбор модели

| Кандидат | Причина попадания в шортлист | Требуемые ресурсы | Приёмочные пороги |
|----------|-----------------------------|-------------------|--------------------|
| **LightGBM** | Проверенный в банковских задачах, быстрая инференс, легко объяснимый SHAP | CPU 2 vCPU + 8 GB RAM | Recall ≥ 0.85, FPR ≤ 0.05, latency ≤ 50 ms |
| **CatBoost** | Хорошая работа с категориальными признаками и missing‑values | CPU 2 vCPU + 8 GB RAM | Same |
| **TabPFN (PyTorch)** | Возможный прирост Recall, быстрый предтренинг, использует GPU | GPU 1 × Tesla T4 | Recall ≥ 0.88, latency ≤ 40 ms (GPU) |

#### Процедура окончательного выбора  

1. **Обучение** на контрольной выборке (10 k операций, 5 % потенциальных схем).  
2. **5‑fold cross‑validation** → собираем Recall, Precision, ROC‑AUC, latency.  
3. **Business‑critical тест** – 1 000 новых операций в прод‑стриме, проверка после расследования.  
4. Выбираем модель, удовлетворяющую **Recall ≥ 0.85**, **FPR ≤ 0.05** и **latency ≤ 50 ms**.  
5. При отсутствии подходящей модели – увеличить объём контрольной выборки до 30 k и повторить.

## Путь получения сигнала‑метки  

Для обучения с учителем выбран **вариант 2 – разметка силами финмониторинга по гайдлайну**:

* Эксперты финмониторинга размечают 10 k операций в течение 6 недел; согласованность κ = 0.87.  
* Плюсы: быстрый старт, уже существующий процесс, высокая точность разметки.  
* Минусы: ограниченный объём, риск смещения от пороговых правил.  

Чтобы компенсировать смещение, параллельно вводится **вероятностная контрольная выборка** (стрaтифицированная случайная) в объёме 5 k операций в месяц, разметка – независимая экспертиза. Данные из этой выборки используются только для валидации и переобучения модели (не попадают в обучающий набор).

# Паспорт инициативы: Выявление подозрительных операций (флагман)

## Постановка задачи
* **Цель:** в реальном времени классифицировать каждую банковскую операцию по вероятности подозрительности и типу риска (транзит, обналичивание, дробление).
* **Выход:** метка `risk_score` (0‑1) + `risk_type` (категория). Метка направляется в очередь финмониторинга, но окончательное решение принимает человек.
* **Ограничения:** решение должно работать в режиме онлайн (latency ≤ 50 ms), сохранять полную конфиденциальность ПДн, предоставлять интерпретируемые объяснения.

## Качество данных
| Аспект | Оценка |
|--------|--------|
| **Источник правильного ответа** | 1) Контрольная выборка ≈ 10 k операций, размеченная экспертами (κ = 0.87). 2) Слабые метки правил (≈ 400 мес.). |
| **Качество** | Экспертная разметка покрывает 5 % потенциальных схем, 95 % «чистых». Ошибки разметки < 5 %. |
| **Объём** | 10 k размеченных + 5 k в контрольном наборе в месяц (стрaтифицированная). |
| **Разметка** | Трёх‑классовая: `clean`, `potential`, `confirmed`. Для обучения используется только `clean` + `potential`. |
| **Смещение отбора** | Операции в обучающем наборе отбираются случайным стратифицированным способом → минимальное смещение. |
| **Репрезентативность** | Стратификация по суммам, типу канала, ОКВЭД, региону. |
| **Право использовать** | Согласовано с DPO, хранение в зашифрованном виде on‑prem, доступ только для ML‑команды. |
| **Владелец** | Финмониторинг + Data‑инженеринг. |

## Данные
| Параметр | Описание |
|----------|----------|
| **Источники** | Транзакционный лог (on‑prem), результаты расследований (экспертные метки), слабые метки правила (пороговые сигналы). |
| **Хранилище** | Защищённый Data‑Lake on‑prem (PostgreSQL + HDFS). Доступ через VPN только к ML‑серверу. |
| **Объём** | ~ 20 млн операций/мес → 600 млн записей в течение года (≈ 2 TB). |
| **Формат** | Таблица: `operation_id, ts, amount, currency, payee, purpose_text, okved, channel, risk_label (если есть)`. |
| **Обеспечение качества** | Автоматический ETL‑проект: проверка дубликатов, валидация схемы, мониторинг «stale»‑данных. |
| **Регулятивные ограничения** | Данные ПДн (ФИО, ИНН) хранятся в РФ, шифрование AES‑256, аудит‑лог. |

## Эксперимент (пилот)
| Пункт | Описание |
|-------|----------|
| **Модель** | LightGBM (baseline) + CatBoost + TabPFN (GPU). |
| **Обучающий набор** | 10 k размеченных операций (80 % train, 20 % val). |
| **Метрики** | Recall ≥ 0.85, FPR ≤ 0.05, ROC‑AUC ≥ 0.92, latency ≤ 50 ms. |
| **Валидация** | 5‑fold CV + hold‑out = 2 k операций. |
| **Бизнес‑тест** | 1 000 новых операций в прод‑стриме; после 30 дней проверка результатов расследования. |
| **Критерий успеха** | ≥ 80 % операций с `risk_score > 0.7` подтверждены как `potential`/`confirmed` в расследовании, при FPR ≤ 5 %. |
| **Сроки** | 6 недели (2 недели – подготовка данных, 2 недели – обучение/валидация, 2 недели – бизнес‑тест). |
| **Ресурсы** | GPU‑инстанс T4 (для TabPFN), 2 × CPU‑vCPU‑2 GB (для LightGBM/CatBoost), 64 GB RAM (ETL). |
| **Ожидаемый результат** | Прототип, готовый к переключению в гибридный продакшен после подтверждения метрик. |


# Паспорт инициативы: OCR документов к кредитной заявке

## Постановка задачи
* **Цель:** превратить скан‑изображения (PDF/JPEG) документов, приложенных к заявке, в структурированный JSON с полями: ИНН, суммы, даты, подписи, реквизиты контрагентов.
* **Выход:** `request_id → { fields: { inn, amount, date, signatures, … } }`.
* **Ограничения:** точность ключевых полей ≥ 95 % (F1), latency ≤ 200 ms, полное хранение данных в РФ, конфиденциальность (шифрование).

## Качество данных
| Аспект | Оценка |
|--------|--------|
| **Источник правильного ответа** | 1 500 вручную размеченных сканов (разметка полей). |
| **Качество** | Cohen κ = 0.92 (согласованность двух аннотаторов). |
| **Объём** | 1 500 (текущий) + планируемый прирост ≈ 500 сканов/неделя в пилоте. |
| **Разметка** | По‑полям (bounding‑box + тип поля). |
| **Смещение** | Набор покрывает 80 % типовых форм (стандартные заявки, выписки). Новые форматы планируется добавить в пилоте. |
| **Репрезентативность** | Выборка пропорциональна типам клиентов (МСП, ИП), регионам, форматам (PDF, фото). |
| **Право использовать** | Согласовано с DPO, хранение on‑prem, шифрование в‑транзите и отдыхе. |
| **Владелец** | Бизнес‑аналитики + IT‑отдел. |

## Данные
| Параметр | Описание |
|----------|----------|
| **Источники** | Система подачи заявок (Document Management System), файлы в формате PDF/JPEG. |
| **Хранилище** | On‑prem GPU‑сервер (NVIDIA A100), зашифрованные тома, доступ только через приватную сеть. |
| **Объём** | 1 500 размеченных + ≈ 2 000 новых в пилоте (≈ 3 TB изображений). |
| **Формат** | `image_id, binary_blob, json_annotation`. |
| **Требования к хранению** | AES‑256, отдельный bucket для сырого изображения и для аннотаций. |
| **Регулятивные ограничения** | Данные ПДн (паспортные данные, подписи) – хранение в РФ, доступ только для ML‑команды. |

## Эксперимент (пилот)
| Пункт | Описание |
|-------|----------|

| **Валидация** | Hold‑out = 1 k новых сканов, не использованных в обучении. |

| **Критерий успеха** | ≥ 95 % F1 + ≤ 120 ms latency (если Tesseract) **ИЛИ** ≥ 95 % F1 + ≤ 200 ms latency (LayoutLMv3). |
| **Сроки** | 4 недели (2 нед – подготовка данных, 1 нед – обучение, 1 нед – валидация + интеграция). |
| **Ресурсы** | GPU A100 (64 GB VRAM) – 1 инстанс, CPU 4 vCPU + 16 GB RAM (для Tesseract). |
| **Ожидаемый результат** | Выбранная модель (по лучшему соотношению точности/latency) развёрнута on‑prem, готова к масштабированию в продакшн. |

# Паспорт инициативы: Прогноз оттока клиентов (Retention)

## Постановка задачи
* **Цель:** предсказывать вероятность ухода клиента в следующем квартале, чтобы сформировать список для таргетированных retention‑кампаний.
* **Выход:** `client_id → churn_probability (0‑1)`. При пороге ≥ 0.6 клиент попадает в список рекомендаций.
* **Ограничения:** модель должна быть объяснимой (importance‑фичи), решения – только рекомендации (не автоматическое отказание), latency ≤ 30 ms, анонимизация данных перед передачей в облако.

## Качество данных
| Аспект | Оценка |
|--------|--------|
| **Источник правильного ответа** | 1) Исторические метки оттока ≈ 9 k (надёжные, подтверждённые). 2) Слабые метки из контрольных выборок ≈ 5 k (потенциальные). |
| **Качество** | Разметка согласована двумя аналитиками (κ = 0.81). |
| **Объём** | 14 k примеров (≈ 5 % отток). |
| **Разметка** | Бинарный `churn / no_churn`. |
| **Смещение** | Исторические метки неполные → дополнительно вводится случайная контрольная выборка (1 % всех клиентов) для уменьшения смещения. |
| **Репрезентативность** | Покрывает все сегменты: размер компании, отрасль, регион, канал взаимодействия. |
| **Право использовать** | Требуется согласие клиентов (opt‑out) + подпись DPO; данные анонимизируются (удаляются ПДн). |
| **Владелец** | CRM‑команда + DPO. |

## Данные
| Параметр | Описание |
|----------|----------|
| **Источники** | CRM‑система (транзакции, взаимодействия), бухгалтерская отчётность, внешний KYC‑сервис (уровень риска). |
| **Хранилище** | Облачный контур Yandex DataSphere (регион = Москва), шифрование, доступ только через IAM‑роли. |
| **Объём** | 14 k записей × ≈ 200 фич (≈ 3 GB). |
| **Формат** | Таблица `client_id, feature_1 … feature_n, churn_label`. |
| **Требования к хранению** | Анонимные клиентские идентификаторы, передача только векторных признаков в модель. |
| **Регулятивные ограничения** | Данные ПДн не передаются в открытый интернет, только в облако РФ. |

## Эксперимент (пилот)
| Пункт | Описание |
|-------|----------|
| **Модели** | 1) LightGBM, 2) CatBoost (target‑encoding), 3) Deep FM (GPU). |
| **Обучающий набор** | 70 % исторических + 30 % контрольных (разметка «слабая»). |
| **Метрики** | Recall ≥ 0.80, Precision ≥ 0.25, ROC‑AUC ≥ 0.86, latency ≤ 30 ms. |

| **Критерий успеха** | ROI ≥ 1.5 при выполнении метрик Recall/Precision. |
| **Сроки** | 8 недель (2 нед – подготовка данных, 3 нед – обучение/валидация, 3 нед – бизнес‑тест и анализ). |
| **Ресурсы** | GPU 1 × Tesla T4 (для Deep FM), CPU 2 vCPU + 8 GB RAM (для LightGBM/CatBoost). |
| **Ожидаемый результат** | Выбор модели с лучшим ROI, готовой к интеграции в CRM‑pipeline (ежемесячный батч‑расчёт). |
